# 歩行方向とオービットカメラの不一致 — 調査記録（2026-10-31）

症状: オービットでカメラを回しても、左スティックのキャラ進行方向がカメラに追従しない。
§1–9 は原因を絞り込んでいた時点の実験記録。§10 で歩行の基準を特定し、§10.1 では 3 方向で歩き始めの 0.3 秒を測定した。壁で止まるため長時間の歩行は未確認。
§11–12 は別エリアの投影と復元の追試。現行版は外部 `.pnach` を必要としない（[アダプターの技術メモ](ADAPTER_NOTES.md)）。

## 1. 初期調査の結論（2026-10-31）

* 歩行は**ゲーム本来のカメラ状態**から決まっており、MOD が書く描画用の視点オフセット
  `0x3403E0` と照準スロット `0x33FC40` は歩行に入らない。これがユーザーの症状の直接原因と考えられる。
* 歩行入力の変換（スティック → ワールド方向）は `FUN_0011BF08`（`0x0011BF08`〜`0x0011C0E4`）にある。
  ただし、そこで読まれる `0x3312F0` / `0x3312F4` を書き換えても歩行方向は変わらなかった（後述 §3）。
* 歩行方向に効いている入力は、**カメラ基点 `0x340370`（ゲームが毎フレーム計算する視点）** の可能性が高い。
  ただし、この値を書いた実験では効果が部分的（約 11.7°）だった。ゲームが毎フレーム先に上書きし、
  歩行処理がその値を読むため、外部からの書き込みが届いていないと見ている（仮説、未検証）。
* 当時の仮説は、歩行処理が `0x340370` を読む命令を特定し、外部 `.pnach` で未使用スロットへ向けることだった。この段階では読み取り先を特定できていなかった。

## 2. 計測の前提

* セーブステート `sstates\base.p2s`（カシル船内の通常フィールド、保護対象）を **読み込みのみ** で使用。
  ステートの保存は行っていない。
* 歩行量は `W` キー（`Keyboard/W` = 左スティック上）を 1.0 秒押して、`0x3312D0`（パーティ座標）の差分で測った。
* ゲームは決定論的に動く（同じ入力・同じステートで同じ変位）ことを確認済み。
* PCSX2 は 1 回再起動した（一時停止からの復帰で GDB が応答しなくなったため）。`EnableCheats` は再起動で
  無効に戻るため、`set_cheats_enabled(true)` + `reload_patches` を都度実行した。

## 4. 効果があったもの（部分的）

| 書き込み先 | 値 | 結果 |
|---|---|---|
| `0x340370`（カメラ基点） | パーティ周りに +90° 回転 | 進行方向 +11.7°（Δ ≈ (8.07, -38.81)）。部分的 |

`0x340370` はカメラ制御ルーチン（書き込み主体 PC `0x001A977C`、VU0 マクロ部の直後）が毎フレーム書く。
PINE の書き込みはそのフレーム内で上書きされ、歩行処理が読むときには届いていないと考えられる。

## 5. 右スティックの挙動（観測）

* 右スティック右（`Keyboard/H`）を 1 秒保持すると、`0x3312F4` が −1.5708 → −0.829 に変わった。
* 同じ間、描画 yaw `0x3403B0`（1.5817）は変わらなかった。つまり、このステートでは右スティックは
  描画カメラを回さず、`0x3312F0/0x3312F4` 系の内部角度だけを動かしている。
* `FUN_0011C0E8`（`0x0011C0E8`）が、パッドのアナログ値（中立 `0x80`）から `0x3312F0/F4` を積算している。

## 6. 関連コードの位置

`0x3312E0` の書き込み監視（Z2）は歩行中に一度も発火しなかった。歩行差分は VU 側か別経路で作られていると見ている。
EE 側の書き込み監視では、VU の書き込みや EE の読み取りは捉えられない（読み取り監視は GDB Z3/Z4 が使えず不可）。

## 7. 次の一手（提案）

1. 歩行処理（VU0 マクロ含む）が `0x340370` を読む命令を特定する。候補は `lqc2` / `lwc1` で、
   ベースレジスタがカメラ構造体 `0x340350` を指すもの。静的に ELF を走査し、`0x0011BF08` 周辺と
   カメラ制御の呼び出し元を重点的に見る。
2. その命令の 16 bit オフセットを、未使用スロットを指すように `.pnach` で変える（照準パッチと同じ方式）。
3. MOD は、そのスロットに「オービットの視点（ベース＋オフセット）」を書く。ゲームはそのスロットに触れないため、
   競合が起きない。
4. 検証: 同じステートで歩行方向を測り、回転量と符号を §2 の手順で確認する。

### 7.2 読み取れたこと

* ゲームのカメラ基点は、スティック操作にも歩行にも連動せず、プレイヤーに対して**固定の幾何**で置かれている
  （カシル船内の基準状態 `base.p2s` で確認）。カメラの yaw に相当する「入力の状態」は、EE メモリ上には見つからなかった。
* 歩行方向は、この固定の基準（ほぼ −Z 方向）から決まっている。
* したがって「ゲーム本体のカメラ状態を書き換える」だけでは歩行は変わらない。基準そのものが
  制御ルーチン（VU0 マクロを含む EE コード）に埋め込まれている可能性が高い。

### 7.3 次にやるべきこと

1. `0x001A9600`〜`0x001A9800` の VU0 マクロ部を復号し、基点ベクトル（目標＋距離×方向）がどの定数・
   どのメモリから作られるかを特定する。
2. その読み取り（`lwc1`/`lqc2`）を `.pnach` で、オービット角を入れた未使用スロットへ向ける。
3. 歩行の基準も同じスロットを読むなら、歩行方向も同時に追従する。

## 9. 2026-10-31 後半: 視点の書き換えは成立、歩行は未追従

### 9.1 視点を作る経路（確定）

* 視点は `FUN_001B0388`（`centre + (sin yaw cos p, -sin p, cos yaw cos p) * dist`）が作り、
  `0x3403A0` に書かれ、`0x340370`（基点）へ複写される。
* 呼び出し元は 8 箇所（`jal 0x1B0388`）。歩行中は `0x1A9610`、`0x1A968C`、停止時は `0x1AC7D0` が使われる。
* 入力は構造体 `0x340350` のオフセット `0x60`（yaw）、`0x64`（−pitch）、`0x68`（距離）、
  `0x8C`（中心ポインタ、既定は `0x33FC50`）。
* `0x3403B0..0x3403B8` は毎フレーム、ブレンド処理（`0x1AC080`）が書き直す。外からの書き込みは残らない。

### 9.2 差し替え（`patches/stock_camera_hook.pnach.txt`、オプトイン）

* 読み取りを専用スロットへ向ける: yaw `0x3403C0` / −pitch `0x3403C4` / 距離 `0x3403C8` / 中心 `0x3403F0`。
* 中心の読み取りは `lw a1,0x8C(base)` を `addiu a1,base,0xA0` に置き換える（ポインタに依存しない）。
* 12 語のパッチ（歩行経路 3 箇所、停止経路 1 箇所）。他の呼び出し元（戦闘・イベント）は触らない。
* 校正（実測）:
  - yaw スロット = `89.85° − 軌道 yaw`（停止時の視線角 −0.8° と一致）。
  - −pitch スロット = `−pitch`（0.2 rad の変化に対し仰角が 11.46° 変わる）。
  - 距離スロット = 軌道距離（視点と中心の距離に一致）。
* 実測結果（`PS2UniversalMod/work` 相当のランタイム試験）: 軌道 0/90/180° で基点の角度は 0.2/90.2/−179.8°、距離は 28.70。
  `restore()` 後は基点角 −0.8°、距離 70.71 に戻った。ユウナは画面中央（ふつうの床、エリア切り替え、左寄りの 3 場面）。

### 9.3 注意（重要）

* 差し替えは `pnach` で常時適用される。MOD が動いていないと、スロットは 0 や古い値のままになり、
  **ゲーム本来のカメラが壊れる**（検証: 補正なしで歩くと進行方向が反転した）。
* 導入するなら MOD を起動したままにする。MOD を閉じると、最後の軌道値が残る。
* エリア切り替えの一部（`base_chara_little_moved_and_cam_big_moved.p2s`）では、基点がこの経路に乗らない。
  そこではオフセット補正が描画を正しく保つ（画面中央は保たれる）。

## 10. 歩行の基準（解決）: 注視点 − 視点

§9.4 の「基準は未特定」は誤りでした。次の実測で基準が分かりました。

* 歩行の向きは、水平面の `normalize(注視点 − 視点)` です。
  * 注視点は `0x33FC20`（ゲームが `0x33FC50`（補間値）から毎フレーム複写する）。
  * 視点は基点 `0x340370`。
* 注視点 `0x33FC20` を、プレイヤー周りに +90° 回すと、歩行の向きが約 +60° 変わりました（最初の 0.1〜0.3 秒）。
  予測（注視点 − 基点）は +64.5° で、一致しました。
* 注視点 `0x33FC50`（補間値）を回しても、歩行は変わりませんでした（補間値は使われていない）。
* 注視点は毎フレーム複写されるため、MOD は 1200 Hz で書き続けます（ゲームの値より後に書けば効く）。

### 10.1 フック＋注視点書き込みの結果

| 軌道 Y | 期待（−Y） | 歩き始め 0.3 秒の進行方向 |
|---|---|---|
| 0° | 0° | −0.2°（移動 7.4） |
| +90° | −90° | −90.2°（移動 7.4） |
| −90° | +90° | +89.8°（移動 9.1） |

その後は壁で止まるため、この部屋では長い歩行が取れません。広い場所での確認が必要です。

### 10.2 実装

* `adapters/ffx2/memory_map.py` の `WALK_TARGET = 0x0033FC20`。
* `engine.py`: 軌道モードのとき、毎ティック `write_walk_target(中心)` を書く。ほかのモードでは書かない
  （ゲームが毎フレーム値を戻すため、止めれば本来の値に戻る）。
* 単体テスト: `test_walk_direction_is_away_from_orbit_eye`（軌道角ごとに向きが −(sin Y, cos Y) になる）。

## 11. other_area_base（2026-11 追加）

* 症状: 視点のずれ、歩行方向の反転、FOV 制御が効かない。
* 原因（確定）:
  * この場所は固定の演出カメラ。視点 `0x340370` は (−59.9, −121.5, −126.2) に固定され、ゲームが毎フレーム書き戻す。
    フックの経路（`FUN_001B0388`）は通らない。
  * 歩行は `注視点 − 基点` で決まるため、基点が固定だと向きが反転する（実測: 軌道 0° で 173°）。
  * 投影の中心が 900（通常 1024）で、画面全体が中心からずれる。投影の倍率は 1024（通常 619）。
* 対応（確定・検証済み）:
  * 注視点を `centre + (基点 − 視点)` にする（`walk_target`）。基点が何であっても `注視点 − 視点` が軌道の前方になる。
    軌道 0/90/180/−90° で歩行方向が −Y どおりになった（歩き始め 0.3〜0.7 秒）。
  * 軌道中は投影の中心を 1024 に固定する（`_hold_projection`、解除時に元へ戻す）。
  * FOV の要求値を `capture_original_fov` で上書きしていた不具合を修正（`settings.fov_deg` は変えない）。
* 未解決: この場所の軌道状態では、投影の倍率（`0x340B00`）を変えても画像が変わらない。
  * 通常の場所（基点）では FOV 93 と 54.7 の差が大きい（平均差 33.5）。
  * 停止時（オフセットなし）の同じ場所では倍率が効く。オフセットだけでは効果が小さい（0.6）。
  * 軌道角・距離の変化は画像に出る（視点は効いている）。倍率だけが効かない。
  * 候補: 描画の投影パケットがこの場所では別の経路で作られている。確定はしていない。

| `0x3403A0`（眼の出力） | `0x1AAEEC` | `sq t0,0(v0)`（`v0 = s1 + 0x50`、`s1 = 0x340350`） | 直前に VU0 経路（`jal 0x2F0E30` / `0x2F0B68`） | 眼を作る別経路で、`FUN_001B0388` ではない。値 `(-59.9, -121.5, -126.2)` は other_area の固定値と一致 |
| `0x340B00`（投影倍率） | 未特定 | — | — | 停止 PC `0x17C058` の `sw $zero,($v0)` は別のアドレスへの書き込み。EE の CPU 書き込みではない可能性 |

所見:
* other_area で基点が固定される原因は、眼の出力 `0x3403A0` を作る `0x1AAE80` 付近の経路が固定値を出していること。
  `FUN_001B0388` 向けの hook が届かない経路である。
* 1 箇所で止める候補は `0x1A977C`。基点と注視点の両方を同時に複写するため、止めると両方に効く。
  ただし、停止時のカメラ（hook なし）の基点も止まるため、素通し（pass-through）を同時に入れる必要がある。
* 投影倍率の書き込み元は未特定。次は `0x1B0908`（投影パケット）の呼び出し元を列挙する。

### 12.1 0x1A977C を NOP にする試験（2026-11-01）

試験: `scratchpad\nop_orbit.py`（other_area_base、yaw 0、pitch 40.9、距離 28.7、use_fov on）。
複写の停止は、基点へ 1234.0 を書いて 0.2 秒後に読んで確認した（NOP 時は 1234.0 のまま、ストック時は −59.92 に戻る）。

| 条件 | FOV 93 と 54.68 の平均画素差 |
|---|---|
| ストック（0x1A977C 有効） | 1.04 |
| NOP（0x1A977C を 0） | 1.5 |
| 対照（NOP、距離 28.7 と 60、FOV 54.68） | 47.6 |

* 対照の差が大きいため、画像の比較は軌道の変化を捉えている。FOV は NOP の有無に関わらず効いていない。
* 基点は NOP 中も固定され（−59.92）、MOD が書く注視点 `0x33FC20` と眼のオフセットで軌道が効く。
* ただし、NOP ではストックのカメラの基点も止まる。素通し（軌道を止めたときに、基点へ眼の出力を写す処理）が無いと、
  ストックの演出カメラは壊れる。導入するなら、この素通しを同時に入れる必要がある。
* 結論: 投影倍率が効かない原因は `0x1A977C` の複写ではない。次は投影パケット `0x1B0908` の呼び出し元と、
  倍率の読み取り箇所を調べる。

### 12.2 投影パケット 0x1B0908 の呼び出し元（2026-11-01）

* `jal 0x1B0908` は EE RAM に 4 箇所ある（`find_pattern 42c2060c`）: `0x1ADFE0`、`0x1AE010`、`0x1AE08C`、`0x1AE0CC`。
* `0x1ADFE0` と `0x1AE010` は、語 `0x342CB4` が非 0 のときだけ通る（`0x1ADFC0` の `beqz`）。other_area と
  base.p2s の両方で `0x342CB4 = 0`。
* 実行停止（`0x1B0908` の exec）: 呼び出し元の `ra = 0x1AE0D4`（`jal` は `0x1AE0CC`）、a0 = `0x33F5E0`。
  **軌道中も、軌道なしのときも同じ呼び出しが起きる。** 軌道で呼び出しが止まるわけではない。
* 呼び出し時の `0x33F5E0` の内容（軌道、FOV 93）: `0x444CCCCD`、`0x446EEEEE`、`0x45000000` など。`0x340B00` の値
  （303.67 = `0x4397D597`）そのものは入っていない。パケットは倍率から変換された値を含むと見られる。

| 条件（other_area、軌道、FOV 93 と 54.68 の平均画素差） | 差 |
|---|---|
| 既定（`0x342CB4 = 0`、`0x340B18 = 0`） | 1.04 |
| `0x342CB4 = 1` | 16.6。ただし画面が水面に変わり、ユウナが映らない（ゲームのカメラ状態も変わる）。採用できない |

* 結論:
  * 「呼び出しが止まるから効かない」という仮説は否定された。軌道中も呼ばれる。
  * `0x342CB4` は FOV の経路を開くが、画面の内容も変える。単純な制御用の語ではない。
  * `0x340B18` は効果がない。
  * フィールドとの差は、パケットを作った後の使われ方、または別の倍率の経路にある。次は `0x33F5E0` の内容を

### 12.4 投影の入力語 0x33F68C（2026-11-01）

* パケット生成（`0x1AE0C0` の経路 B）の入力は `a1 = 0x33F670`。語 `0x33F68C` はその 7 番目（オフセット 0x1C）で、
  パケットの語 51 と同じ番地である。出力と入力が重なっている。
* 経路 B の条件: `0x342CC0 = 0` かつ `0x33F660 = 0`（両方とも other_area で成立）。`0x342CB0` は `0x33FBC0`（上方向の基準）を指す。
* 書き込み監視: 停止位置 `0x1A99C4` は命令と一致せず信頼できない。書かれた値（f0）は 900.0（other_area の中心の値）。
* 中心 `0x340B30` を 700 や 1024 に書いても、`0x33F68C` は 0.3 秒後も 900.0 のまま。中心には追従しない。
* 試験（other_area、場面を読み直して実施。フレームは基準の場面と一致）:

| 条件 | 基準との画素差 | 所見 |
|---|---|---|
| `0x33F68C` を 303.67 に保つ（FOV 93） | 0.9 | 変化なし |
| `0x33F68C` を 618.93 に保つ（FOV 54.68） | 46.4 | 画像は変わるが、ユウナが小さく映る広い構図。ズームとしては正しくない |

* 保つ書き込みの読み戻しは、どちらも 1024（`0x44800000`）だった。ゲームが毎フレーム書き戻している。
* 連続した 3 枚（618.93 を保った状態）: 1 枚目と 2 枚目は差 0.18 でほぼ同じ。3 枚目は両方と差 58.8 前後で別の見え方。
  画面が、強制した見え方と別の見え方を交互に出している（ちらつき）。ユーザーの目視とも一致する。
  保つ書き込みはゲームの書き込みと競合するため、この方法では効果を採用できない。
* 結論:
  * `0x33F68C` は投影の入力のひとつだが、ゲームが毎フレーム書き戻すため、外からの書き込みでは制御できない。
  * 次は `0x33F68C` の書き込み元（`0x1A99xx` 付近）を特定し、書き込みを MOD の値へ逸らす（walk target と同じ方法）。

### 12.5 書き込み元の特定と差し替えの試験（2026-11-01）

* 語 `0x33F68C` の値の流れ（`0x1A9820` 以降）:
  * `0x1A9830`: `v0 = k·0x30`（`k` はスタックの添字）、`s0 = s7 + v0 + 0xF38`。`k=0` の行は `0x340AF8`、`k=1` の行は `0x340B28`。
  * `0x1A985C` `lwc1 $f0,8($s0)`: 行の +8 を読む。`k=0` は `0x340B00`（scale）、`k=1` は `0x340B30`（centre）。`0x1A9864` の `swc1` が `0xF20`（`0x340AE0`）へ書く。
  * `0x1A9934` `beqz`: フラグ `0x33F660` が 0 なら `0x1A9944` で `0xF20` を読む。0 以外なら `0x500000 − 0x1CC0` の定数を書く。
  * `0x1A9954`/`0x1A9968`/`0x1A9978`: `0xF1C` を経由して `0x33F670 + k·0x1C0 + 0x1C` に書く（`k=0` で `0x33F68C`）。
* other_area（フラグ 0）では `k=1` の行が使われ、語は centre `0x340B30`（900）になる。このため scale `0x340B00` を変えても語は変わらなかった。
* 差し替え: `0x1A985C` を `lwc1 $f0,8($s0)`（`C6000008`）から `lwc1 $f0,0xF40($s7)`（`C6E00F40`、`0xF40` は `0x340B00`）へ変える。
  * 語 `0x33F68C` は `0x340B00` に追従した（303.67 と 618.93 を 0.8 秒保って確認。ゲームは `0x340B00` を書き換えなかった）。
  * 画像（other_area）: 303.67 と 618.93 の差 54.8。618.93 の連続 2 枚の差 3.4（定常の揺れ）。効果は明確に見える。
  * pass-through: 差し替えたうえで `0x340B00 = 900` にすると、元の命令との差は 1.3（ノイズ範囲）。
* 注意と未決:
  * 差し替えは `k=1` の行にも効く。`k=0`（field 側で読まれる行）は元から `0x340B00` を読むため変わらないが、field でのフラグ値は未確認。
  * （§12.6 で採用を変えた: orbit が off のときは `0x340B00` に書かず、命令そのものを stock に戻す。）
  * runtime の `_hold_projection` は中心を常に 1024 にしている。other_area では語が中心に依らなくなるが、中心の画像への効果は未確認。
  * 差し替えは pnach ではなく runtime から入れる（§12.6）。

### 12.8 「未適用」と「クラッシュしやすい」の原因調査（2026-11-01）

* 未適用になる理由（確定）: pnach の語は起動時と再読込時にしか書かれない。セーブステートを読むとゲームの RAM が
  戻るので、語も stock に戻る。実ログでも、`base.p2s` の読込後は視線が stock、hook が False だった。GUI は「未適用」と表示していた。
* クラッシュの候補（コードから。実際に起きたかは未確認）:
  1. pnach で視線とフックが有効なのに runtime が動いていないと、参照する slot（`0x3403C0`〜、`0x33FC40`）は誰も更新しない。
     起動直後はゼロのため、stock のカメラが不正な値を読む。
  2. GUI を閉じたとき、`restore()` は slot に stock 値を一度だけ写したが、語は残した。その後 slot は凍結し、stock のカメラが追従しなくなる。
  3. PINE の応答がずれる: タイムアウトした要求のソケットを残していた。遅れて届いた応答を次の読み出しが受け取り、
     以後すべての読み出しが 1 つずれる。オフセットや投影に誤った値が書かれうる。→ ソケットを作り直すように修正。
     `tests/test_pine_backend.py` が修正前の挙動で失敗することを確認した。
  4. 投影元の書き込みが失敗すると毎 tick（約 1200 回/秒）再試行していた。→ 1 秒待つように変更。
  5. 投影元の書き込みは、未知の語にも上書きしていた。→ 比較して書くように変更。
