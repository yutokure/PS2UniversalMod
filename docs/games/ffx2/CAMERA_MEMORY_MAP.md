# FFX-2 カメラ・メモリマップ

対象: FINAL FANTASY X-2 (Japan) `SLPS-25250` / CRC `8A6D7F14`
ベース: PCSX2 v2.7.499-12-g7235a0446（`fork-B056de99`）+ PINE 28011 + EE GDB 10501

すべてのアドレスは **EE メインメモリの物理オフセット**（PINE にそのまま渡せる）。
値は float32。特に断りがない限り vec4（x, y, z, w）単位。

---

## 1. 確定アドレス

### 1.0 レンダーカメラオブジェクト（`0x340350` 基点）

実測で判明した構造。ゲームのカメラ制御が毎フレーム更新する。

| オフセット | アドレス | 内容 | 外部から書けるか |
|---|---|---|---|
| +0x00 | `0x340350` | カメラ管理用フィールド | — |
| +0x10 | `0x340360` | **レンダー視点 (x,y,z,w)** | ✅ 高確率で反映 |
| +0x20 | `0x340370` | ゲームが計算した視点 | （ゲームが毎フレーム書く） |
| +0x30 | `0x340380` | 注視点 | ❌ 描画に未使用 |
| +0x60 | `0x3403B0` | **yaw**（ラジアン） | ⚠️ 約10〜15%のフレームのみ反映 |
| +0x64 | `0x3403B4` | **-pitch**（ラジアン） | ⚠️ 同上 |
| +0x68 | `0x3403B8` | 未確定（距離系） | ❌ 効果なし |
| +0x6C | `0x3403BC` | 未確定（前後移動系） | ⚠️ ドリー相当の変化 |
| +0x90 | `0x3403E0` | **視点の加算オフセット** | ✅ **決定的** |

**yaw / pitch の同定根拠**: レンダーの forward を
`f = normalize(target - eye)` として
`-pitch = asin(f.y)`、`yaw = atan2(-f.z, f.x)` を計算すると、
`0x3403B4 = -0.480882`（計算値と完全一致）、`0x3403B0 = 1.582058`（同）となる。
さらに `0x3403B4` に +0.5 rad 書くと画面が大きくピッチ回転し、
`0x3403B0` に +0.8 rad 書くとヨー回転したフレームが得られた
（`reports/probe_block/i1_d0.5.png`, `reports/probe_yaw/yaw0.8.png`）。

**反映率の実測**: 角度を保持し続けてもヨーは 8 フレーム中 1、
ピッチは 6 フレーム中 1 しか反映されない。
一方 `0x3403E0`（視点オフセット）と `0x340360`（視点）はほぼ毎フレーム反映される。
→ **視点はフレーム後半に読まれ、角度は前半（カメラ更新直後）に読まれる**と推定。

### 1.1 視点オフセット注入（本 MOD の中核）

Ghidra による逆コンパイル（`FUN_001b0008`）:

```c
void FUN_001b0008(undefined1 (*param_1)[16], undefined1 (*param_2)[16], undefined1 (*param_3)[16])
{
  auVar1 = _lqc2(*param_2);          // 0x340370
  auVar2 = _lqc2(*param_3);          // 0x3403E0
  auVar1 = _vadd(auVar1, auVar2);    // VU0 マクロモードのベクトル加算
  *param_1 = auVar1;                 // 0x340360
}
```

実測でも確認済み:

```
offset(0x3403E0) = 0        -> eye = (-1.3086, -26.0506, 131.9051)
offset            = (20,0,0) -> eye = ( 18.6914, -26.0506, 131.9051)   ← ちょうど +20
offset を 0 に戻す           -> eye = (-1.3086, -26.0506, 131.9051)
```

**なぜこれが決定的か**: ゲーム自身が毎フレームこの加算を行うため、
外部からは「差分」を書くだけでよい。描画直前にゲームが加算するので、
書き込み競合（レース）が原理的に発生しない。
`0x3403E0` はゲームが 0 以外を書かないため、書いた値は保持される。

### 1.2 カメラ制御が「静止時は動かない」こと

プレイヤーが停止しているとカメラ制御自体が走らず、上記の加算もスキップされる。
そのためランタイムは **オフセット注入と直接書き込みの併用** で運用する。
両者は同じ目標値を持つので、どちらが勝っても描画結果は一致する（ちらつきゼロ）。

## 3. 座標系（実測）

* **+X**: 画面右方向
* **+Y**: **下方向**（カメラは注視点より小さい Y＝「上」にいる）
* **+Z**: カメラから見て奥（既定カメラは注視点より +Z 側にいる）

既定フィールドカメラの実測値:

```
target = (-0.7377,  -7.2519, 110.2479)
eye    = (-1.3086, -26.0506, 131.9051)
offset = (-0.5709, -18.7987,  21.6572)   |offset| = 28.69
yaw    = atan2(-0.5709, 21.6572)  = -1.51 deg
pitch  = atan2( 18.7987, 21.6703) = +40.95 deg（正 = 注視点より上）
```

Orbit カメラの式（`core/camera_math/orbit.py`）:

```
eye.x = target.x + sin(yaw)*cos(pitch)*distance
eye.y = target.y - sin(pitch)*distance      ← Y が下向きなので減算
eye.z = target.z + cos(yaw)*cos(pitch)*distance
```

## 5. 実測: 場所による「中心ズレ」の回避

ゲーム側カメラがスクリプトで動く場所（カシル船内の通路）では、
ゲームの注視点 `0x340380` がユウナの位置と一致しないことがある。
実測例:

```
player anchor = (-0.37, -12.25, 85.6)
game eye      = (-1.57, -28.78, 112.68)
game target   = (-0.37,  -7.25,  85.6)   <- この場所では x/z が一致していた
```

一致しない場所でも回転中心がブレないよう、本 MOD は
**中心 = player anchor + (0, look_height, 0)** とし、注視点も同じ点へ書く。
`tools/centering_check.py` で yaw 0/90/180/270 の 4 枚を取得し、
被写体が画面中心に留まることを目視・ピクセル統計で確認できる。

# v2 追記（2026-10-31）: 視線の実体と競合の無い注入

上記の「注視点 `0x340380`」は**プレイヤー基準点**であって、描画の注視点ではありません。
v2 で視線経路を特定したので、以下を正とする。

## 視線を作る関数

```
FUN_001b07a0(out = 0x33F620, eye = 0x340360, target = 0x33FC10, up = 0x33FBC0, roll = f12)
    0x1B07F8  lqc2 $vf4, 0x00($s2)    ; eye
    0x1B07FC  lqc2 $vf5, 0x00($s1)    ; target   <- .pnach で 0x30($s1) に変更
    0x1B0800  lqc2 $vf8, 0x00($s0)    ; up
    forward = normalize(target - eye)
```

実測照合:

| 量 | 値 |
|---|---|
| eye `0x340360` | (-0.266901, -25.852787, 125.626915) |
| target `0x33FC10` | (0.398717, 0.026899, 59.550465) |
| normalize(target-eye) | (0.00938, 0.36467, -0.93109) |
| 描画基底 `0x53ADA0` | (0.00938, 0.36467, -0.93109) |

`0x33FBC0 = (0, -1, 0)`。FFX-2 のワールドは **+Y が下向き**。

## 追加アドレス

| アドレス | 意味 | 書き込み可否 |
|---|---|---|
| `0x340380` | プレイヤー基準点（カメラが追う点） | 読取のみ |
| `0x33FC10` | 描画が使う注視点（毎フレーム上書き） | 競合する |
| `0x33FC40` | **未使用スロット**（.pnach で読み取り先） | **競合なし**（実測: 数秒保持） |
| `0x33FBC0` | up 参照 `(0,-1,0)` | 読取のみ |
| `0x3403E0` | 視点の加算オフセット（ゲームは 0 しか書かない） | **競合なし** |
| `0x001B07A0` | look-at 行列ビルダ | — |
| `0x001B07FC` | 注視点ロード命令（パッチ対象） | — |

パッチ: `patch=1,EE,001B07FC,word,DA250030`（`0xDA250000` → `0xDA250030`）。

## 出力専用（書いても描画は変わらない）

`0x53AD80` 基底 / `0x53ADA0` forward / `0x53ADB0` 視点ミラー / `0x53ADD0` look /
`0x33F620` ビュー行列 / `0x3403B0` yaw・`0x3403B4` -pitch・`0x3403B8` dist /
`0x3312C0` 補助オービットカメラの出力（`FUN_0011c3d8` が `0x3312F0/0x3312F4` から計算）。

`FUN_001b0388`（yaw/pitch → 位置）は**初期化専用**。フィールドでは到達不能
（`0x1A956C` で分岐し `0x1A95F8` のガードが未初期化 `$s5` と比較するため）。
強制的に通すと 1 回呼ばれるたびに視点が `dist` ぶん後退する（実測 |Δ| = 70.9669 = dist）。
`0x001A95F8` のガードは外してはいけない。

# v3 追記（2026-10-31）: 歩行入力に関わるアドレス

v2 の「出力専用」の分類は、歩行入力については訂正が必要。詳細は `docs/games/ffx2/WALK_DIRECTION_INVESTIGATION.md`。

| アドレス | v3 での扱い |
|---|---|
| `0x3312F0` / `0x3312F4` | `0x0011BF08`（歩行入力変換）が読む。`0x0011C0E8` が右スティック系の値から積算する。書き換えても歩行方向は変わらなかった（実験で確認） |
| `0x340370` | カメラ基点。`0x001A977C` 付近（VU0 マクロ部）が毎フレーム書く。歩行方向に効く可能性が高いが、書き込みは上書きされるため未確定 |
| `0x340480` | カメラ制御内で sin/cos に渡される値。書き換えてもベース視点は変わらなかった |
| `0x3403B0` | 描画 yaw。書き換えても歩行は変わらなかった |
| `0x3312E0` | 歩行差分。`0x0011C0C4` で書かれるが、歩行中の EE 書き込みは監視で捉えられなかった（VU 側の可能性） |
